The review slot's findings have been numbered five different ways across four rounds, and
only one of them (`S<NN>`) is cited from code. This table is the registry for that one: the
parity checker parses the id column below and scans every tracked `.md`, `.yml`, `.yaml`
and `.go` file plus the Makefile for `A3's S<NN>`; a cite naming an id with no row here
fails the build (`scripts/check-parity-matrix.py`, the finding-id section). Before this
table, a Go comment saying *"the `captured_at < ?` is A3's S26"* pointed at a paragraph in
a commit-message body — a different repository object, unresolvable without a `git log`,
and unresolvable at all for the ids that were never written down anywhere but a subject line.

**A row's cites are frozen at the rev the row names; they are not live references (ruled, on A2's question).**
The index's job is to make `A3's S<NN>` resolvable and to record what was found and what fixed it. The cites in
the `against` and `finding` columns were verified at the rev in the row's `filed in` / `fixed by` columns, so
they get checked with `git show <rev>:<path>`, not against the worktree -- S52's `internal/api/dto/series.go:63`
and `api/openapi.yaml:2941-2949` stay as filed even though those two locations are `internal/api/dto/series.go:75`
and `api/openapi.yaml:2958` today. Retargeting a closed row would make it describe a state that existed at no
commit: the number is correct now but was a different number at the commit named in `fixed by`. The live
artifacts are `requirements.md`'s R-cells and `docs/agents.md`'s ownership table -- both describe the current
code, so both do get retargeted, and that is what `c4affd2` did to R8.3. A2 stops filing cite decay against
index rows; the S52 row's status flip to `fixed` is the only change that commit owed it.**When `filed in` names no rev** -- the 85 rows that read `this review` in either spelling (backticked: S121-S122, S126-S127, S130-S145; bare: S39-S51, S69-S120) -- the check rev is the row's `fixed by` cell, and a row with neither (S33 `—`, S36/S41/S51 `open`) has no rev to check against, so its cites are the author's word: the S51 class, not a new one. The only fix for that class is the row; there is no address to retarget and no rev to freeze. **Cite form, ranked (ruled, on A2's question about fanning out the `` `path:N` (`Symbol`) `` form from `fbd75b2`).** The parenthetical is not checked: `CITE_A` parses the path and the number and the symbol sits outside the backticks, so `fbd75b2`'s run is byte-identical to `ac04fcd`'s (871 resolved · 0 wrong) -- the annotation adds a claim the checker never verifies. Rank the forms by what the checker can check, not by which slots happen to share the habit: **(1) form B**, `` `path` § "Heading" (:158-253) ``, is the only content-verifying form and is required wherever the target has a heading to name; **(2) form A with the symbol parenthetical** is required for a cite into a file that gets *inserted into* and has no heading at the cited line (Go declarations, YAML scalars, TS docblocks) -- that is the `server.go:207→:230` class, repaired twice in two days by `ac04fcd` and `fbd75b2`; **(3) bare form A** is sufficient only in files that are appended to and never inserted into, which is this file's own rows and `requirements.md`'s R-cells. So the condition A2 asked for is the target file's insertion behaviour, not the author and not the round; filed under R14.4's existing scope (docs/ holds reviews/) rather than as a new ID. **Two addenda from the same thread.** *(a) The backticks are a precondition of all three forms* (A2's ask, proven by their mutation): `CITE_A` (`scripts/check-parity-matrix.py:353`) requires a literal backtick on both sides of `path:N`, and `path_citations` (:406) builds the report-only tier from CITE_A and CITE_B only -- a path written bare in prose is not a cite in any form, so a file reports clean while its prose cites resolve to nothing. Five css cites in `cdfce3e` were exactly that (tier: 235 checked); `bbec6d4` backticked them (240 checked), the +5 their single-file mutation predicted. *(b) Side-naming goes outside the backticks* (A6's ask, ruled on the regex rather than adopted verbatim): `P` matches only `[A-Za-z0-9_./-]+\.(ext)`, so the side inside the token -- `` `HEAD:web/src/api/client.ts:426` `` -- matches nothing and the label destroys the cite it annotates; write it outside, as in HEAD: `web/src/api/client.ts:426`. Required only when the file is dirty and the worktree/index/HEAD versions differ at the cited line -- the `eabd459` disjunction resolves a cite from any of the three, so a clean tree needs no side. The same clause has a second half: the walk's file set is `git ls-files -z` (:264, with the `rglob` fallback at :268 only when git fails), so a backticked cite in an *untracked* file is invisible too -- A2 measured `internal/api/probe_presence.go` with two backticked cites at 240 while untracked and 242 once committed as `7833653`. The count moves at commit time, not at write time, so running the checker against a dirty tree under-reports the author's own cites. *(c) A reference inside a string literal is not a cite* (A1's ask on `internal/collector/bloat_test.go:140` and `internal/collector/bloat_test.go:143`, ruled): the backticks in `` `path:N` `` are markdown inline-code delimiters, which cost nothing in a Go comment or a markdown cell because nothing there reads them as content, but inside a Go string literal they become part of the program's observable output -- a `t.Errorf` format string gains two backtick characters in every failure message it prints. Where backticking changes the artefact, the reference belongs in the comment above the statement, not in the string; a `path:N` left inside a string literal is program text, is not a cite in any form, and its author owes no fix. Same R14.4 scope as (a) and (b).

## The collision the charter did not anticipate

The charter's reporting rule is *"Number findings with a prefix that cannot be mistaken for
a slot name. `S1, S2, …` is the default, and `A1`–`A6` are not available as finding IDs —
they are the six slots."* It avoids the collision it names and walks into two others:

- **`S1`–`S10` are data sources.** requirements.md §3.2's source table uses `S1`…`S10`
  (`S1` = `Cluster.status`, `S2` = Direct SQL), and `internal/collector/collector.go:72`
  encodes it as `SourceClusterStatus SourceID = "S1"`. So at HEAD, `S1` names both
  `Cluster.status` and the R8.4 `meta.total` ruling, and `S3` names both a source and the
  inert-chart finding — in the same commit, `f08b6ac`.
- **`D20's S5`–`S12`** are findings scoped to one deviation, cited from `internal/collector/*.go`.

The collision is bounded and the bound is exploitable: source ids stop at S10, so **S1–S10
are ambiguous** and **S11 and above are unambiguous**. Every finding filed since the
Phase 1a round has been at S21+, which is why the qualified form has worked so far. The
rule this table adopts, and the amendment owed to `.claude/agents/a3-review.md`: a finding
id is written `A3's S<NN>` in prose, and a new review round **starts above S10** rather
than at S1. The checker enforces the qualified form's resolution; it does not yet flag a
bare `S1`–`S10` outside §3.2's table as ambiguous, and that gap is stated rather than
hidden.
