# Finding index — every `A3's S<NN>` id, what it said, and what became of it

The review slot's findings have been numbered five different ways across four rounds, and
only one of them (`S<NN>`) is cited from code. This table is the registry for that one: the
parity checker parses the id column below and scans every tracked `.md`, `.yml`, `.yaml`
and `.go` file plus the Makefile for `A3's S<NN>`; a cite naming an id with no row here
fails the build (`scripts/check-parity-matrix.py`, the finding-id section). Before this
table, a Go comment saying *"the `captured_at < ?` is A3's S26"* pointed at a paragraph in
a commit-message body — a different repository object, unresolvable without a `git log`,
and unresolvable at all for the ids that were never written down anywhere but a subject line.

**A row's cites are frozen at the rev the row names; they are not live references (ruled, on A2's question).**
The index's job is to make `A3's S<NN>` resolvable and to record what was found and what fixed it. The cites in
the `against` and `finding` columns were verified at the rev in the row's `filed in` / `fixed by` columns, so
they get checked with `git show <rev>:<path>`, not against the worktree -- S52's `internal/api/dto/series.go:63`
and `api/openapi.yaml:2941-2949` stay as filed even though those two locations are `internal/api/dto/series.go:75`
and `api/openapi.yaml:2958` today. Retargeting a closed row would make it describe a state that existed at no
commit: the number is correct now but was a different number at the commit named in `fixed by`. The live
artifacts are `requirements.md`'s R-cells and `docs/agents.md`'s ownership table -- both describe the current
code, so both do get retargeted, and that is what `c4affd2` did to R8.3. A2 stops filing cite decay against
index rows; the S52 row's status flip to `fixed` is the only change that commit owed it.**When `filed in` names no rev** -- the fourteen rows that read `this review` (S39-S52) -- the check rev is the row's `fixed by` cell, and a row with neither (S33 `—`, S36/S41/S51 `open`) has no rev to check against, so its cites are the author's word: the S51 class, not a new one. S52's row also carried a malformed cell pair -- `fixed by` read `-- fixed` with the status column absent, five cells where the header has six -- and it now reads `filed in` = `136c059`, `fixed by` = `d0ea2c4`, `status` = `fixed`. The two revs are not interchangeable: `internal/api/dto/series.go:63` is the `LockTimeSeconds` field at `136c059`, a comment line at `9945203` (`d0ea2c4`'s parent, the field at :70) and a different comment at `d0ea2c4` (the field at `:75`), so the pre-fix cites verify at the rev the finding was filed against, not at its fix -- which is why the fallback names `filed in` first and reaches for `fixed by` only when `filed in` is prose with no rev in it. **And the other half of the ledger: a cite whose row was never written.** The rule above freezes cites *on* rows; S53 and S54 were filed in the `b840e06` review and rowed two rounds late, which is what A2 caught when `web/src/pages/ClusterDetail.tsx:195` cited `A3's S54` and `FINDING_CITE_RE` (`scripts/check-parity-matrix.py:1150`) — which scans `.ts/.tsx` as well as the `.md/.yml/.go` set — turned the gate red. The only fix for that class is the row; there is no address to retarget and no rev to freeze.

**Which ids have rows (the coverage claim).** The table holds 117 rows -- the same number
`scripts/check-parity-matrix.py` prints as `finding ids:`, so a disagreement between the two is a stale
header rather than a missing row -- covering every id in the S1-S78 range except five: S4, S15, S19, S20 and S24. Those five cannot be shown to have been minted
as findings at all, so there is no finding text to row. `S4` occurs three times in
`docs/reviews/round-1-architecture.md` (`:91` "validated through S1/S4 only", `:227` "Our source table
(S1-S9) contains no log source: S1 is the CR, S2 SQL views, S3/S4 the", `:380` "**S4's auth model**") and
all three are the requirements.md §3.2 *data-source* id, not a finding id -- `internal/collector/collector.go:72`
defines `SourceClusterStatus SourceID = "S1"` and the table runs to S10, which is the collision the
qualified-cite rule (`A3's S26`, never a bare `S26`) exists to prevent. The other four appear in no
tracked file as `A3's S<NN>` cites and in no commit body, verified by `git grep 'A3's S<id>' HEAD`
returning zero files for each. The thirteen rows added here (S5-S14, S16-S18) close the gap between the
round-1 and round-2 findings and the table: every path and path:line in those thirteen `against` cells
was verified against the rev in the row's own `filed in` / `fixed by` cell before the rows were written
(13 rows, 0 failures), which is the frozen-cite rule applied at write time rather than at check time.

## The collision the charter did not anticipate

The charter's reporting rule is *"Number findings with a prefix that cannot be mistaken for
a slot name. `S1, S2, …` is the default, and `A1`–`A6` are not available as finding IDs —
they are the six slots."* It avoids the collision it names and walks into two others:

- **`S1`–`S10` are data sources.** requirements.md §3.2's source table uses `S1`…`S10`
  (`S1` = `Cluster.status`, `S2` = Direct SQL), and `internal/collector/collector.go:72`
  encodes it as `SourceClusterStatus SourceID = "S1"`. So at HEAD, `S1` names both
  `Cluster.status` and the R8.4 `meta.total` ruling, and `S3` names both a source and the
  inert-chart finding — in the same commit, `f08b6ac`.
- **`D20's S5`–`S12`** are findings scoped to one deviation, cited from `internal/collector/*.go`.

The collision is bounded and the bound is exploitable: source ids stop at S10, so **S1–S10
are ambiguous** and **S11 and above are unambiguous**. Every finding filed since the
Phase 1a round has been at S21+, which is why the qualified form has worked so far. The
rule this table adopts, and the amendment owed to `.claude/agents/a3-review.md`: a finding
id is written `A3's S<NN>` in prose, and a new review round **starts above S10** rather
than at S1. The checker enforces the qualified form's resolution; it does not yet flag a
bare `S1`–`S10` outside §3.2's table as ambiguous, and that gap is stated rather than
hidden.
