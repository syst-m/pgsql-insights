# v0.3.0 review — architecture & spec maintenance (reviewer A3, opus)

2026-11-20 · reviewed: `requirements.md` `0.3.0` (`7808a24`, 876 l) + `IMPLEMENTATION.md` v0.3.0
+ the untracked `web/` tree · scope: the v0.2.0 → v0.3.0 delta (Phase 1 split into 1a/1b, SPA moved
from Phase 5 to 1b) · prior: `docs/reviews/round-1-architecture.md` (A3, 7 B / 10 M / 8 N)

## Verdict

**Approve with changes — 4 blocking, 8 major, 6 minor.** The split itself is right and D13's
reasoning holds up under the roster arithmetic. What is not right is that the split was made in
§7.2 and §7.3 and not propagated to the four documents and five sections that are supposed to be
*generated from* it. Every one of the four blocking findings is a traceability defect of exactly
the class §7.3's preamble claims to have eliminated (A3-M7 in v0.1.0), and three of the four are
newly introduced or newly made acute by v0.3.0. A1 and A4 have both started, so each of these is
one line to fix today and a reconciliation to write in a week.

The second theme: **1b's acceptance criteria are written against an artifact that does not yet
exist and is owned by a different agent.** `web/` is untracked, has no `embed.go`, no
`playwright.config.ts` and zero test files, and the Go binary serves four routes and no `/`.
That's fine for day one of a phase — it is not fine for criteria that are already written and
already marked 🔄 in `IMPLEMENTATION.md` §3.

## Findings: BLOCKING

### B1 — R10.12 is defined in §4 and scheduled in **no phase**, and Phase 1b's acceptance cites it

§7.3's R10 row enumerates 27 of R10's 28 IDs:

```
| R10 | 10.1, 10.2, 10.4, 10.16 → 1b · 10.3, 10.13, 10.14, 10.15, 10.17, 10.24 → 5 ·
        10.8, 10.9, 10.25, 10.26 → 6a · 10.5, 10.6, 10.7, 10.18–10.23, 10.27, 10.28 → 6b ·
        10.10 → 7 · 10.11 → 8 |
```

**R10.12 is absent** — from §7.3 and from every §7.2 row. Yet:

- Phase 1b's acceptance criteria say: *"R16.7 harness runs in CI and has **≥1 passing visual test
  per R10.12 state it can reach at this phase**"* — a criterion that cites an ID the same row's
  Req IDs column (`R10.1, R10.2, R10.4, R10.16, R16.7`) does not include.
- §8's `freeidp` row lists R10.12 among "Requirements proven".
- R10.12's own text says it is *"Verified by R16.7's visual-regression suite"* — and R16.7 is now
  at 1b, so the verifier exists at 1b while the requirement is scheduled nowhere.

This is the exact A3-M7 defect class the coordinator asked about: an ID defined in §4 and
scheduled in no phase, in a table whose entire purpose is to make that impossible. It was already
true in v0.2.0; v0.3.0 makes it acute by putting R10.12 in a phase's acceptance text.

**Fix:** `10.12 → **1b** (Fleet's four states) · re-validated at **5**, **6a**, **6b**`. All four
of R10.12's states (empty, loading, partial, unavailable) are reachable on the Fleet page at 1b
given the reference environment — `web/src/api/fixtures.ts` already encodes the "unavailable" one
by setting `metrics.source: "unconfigured"` on all four clusters. Add R10.12 to 1b's Req IDs.

### B2 — R11.8 is in §7.2's Phase 2 row and in §6, but missing from §7.3's R11 row

§7.3's R11 row reads `| R11 | 11.1–11.7, 11.9–11.16 → **0** (11.6 also re-validated at **5** and
**9**) |` — 15 of R11's 16 IDs. **R11.8** (config precedence + `pgsi config dump`) is skipped.
Meanwhile §7.2's Phase 2 Req IDs column lists `R11.8`, §6's `InsightsConfig equivalents` row says
`2 (R11.8)`, and `IMPLEMENTATION.md`'s Phase 0 row reproduces the same `11.1–11.7, 11.9–11.16`
list. So the two documents that §7.3 says are generated *from* it both disagree with it.

**Fix:** `| R11 | 11.1–11.7, 11.9–11.16 → **0** · **11.8 → 2** · (11.6 also re-validated at **5**
and **9**) |`. R11.8 belongs at Phase 2 (it is the config system, which lands with the collector
framework), not Phase 0 — so the Phase 0 rows in both files are the ones carrying the error.

### B3 — "every ID in §4 appears exactly once" is false for R8 and R12; the convention exists and isn't applied

The spec already has a notation for an ID that legitimately spans phases, and uses it twice
correctly: R11's `(11.6 also re-validated at **5** and **9**)` and R9's `9.7 (partial) → **2** ·
9.7 (complete) → **7**`. Two rows violate it:

- **R8**: `8.1, 8.7 → **1a** · 8.2, 8.4, 8.5 → **3** · 8.1–8.9, 8.10, 8.11 → **5** (full surface)`.
  R8.1 and R8.7 appear in 1a *and* in the 5 range; R8.2/8.4/8.5 in 3 *and* in 5. The
  `(full surface)` parenthetical is a comment, not the annotation form — it doesn't say which of
  the two is the assignment and which is the re-validation.
- **R12**: §7.3 says `12.1–12.3 → **0**`, but Phase 1a's Req IDs column in §7.2 *also* lists
  `R12.1–R12.3`. Two phases, no annotation, and §7.3 (the claimed source) names only one of them.

**Fix:** state the convention in §7.3's preamble — *an ID may appear in more than one phase only
when annotated `X (partial) → n` for a partial implementation or `X also re-validated at m` for a
full one* — then annotate R8 (`8.1, 8.7 → 1a · also re-validated at 5`; `8.2, 8.4, 8.5 → 3 · also
re-validated at 5`) and decide R12.1–12.3's real owner (RBAC ships with the chart at 0; if 1a
re-validates it against the real client, say so).

### B4 — R10.4 cannot be satisfied at 1b; 1b's acceptance silently narrows it to a subset

R10.4 requires the Fleet table to show *"phase, instances, PG major, **TPS, p95 latency,
connections %, disk %, and the top finding**"*. `/api/v1/clusters` as R1.5 defines it returns
*namespace, name, phase, phaseReason, instances, readyInstances, servingInstances, currentPrimary,
PG major, instance list…, conditions, cert expirations, PVC list, services, Poolers* — **none of
the four metric columns and no top finding**. Their sources are R9.4 (Phase 4), R2.2/R5.3
(Phases 2/7) and R7.2–R7.6 (Phase 8).

Phase 1b's acceptance lists only *"health distribution, sortable table with phase/instances/PG
major"* — 3 of the 8 required columns. So 1b can be marked done with R10.4 two-thirds unimplemented,
and R14.8 will then record R10.4 as validated at 1b on a partial implementation, which is the
failure mode R14.8's `not-started | in-progress | implemented | validated` vocabulary exists to
prevent.

`web/src/api/fixtures.ts` proves the point from the other side: A4 has already built `tps`,
`p95LatencyMs` and `connectionsPct` columns that render `—` because `metrics.source` is
`"unconfigured"`. That pattern is the fix.

**Fix:** either split it — `R10.4a` inventory columns → **1b**, `R10.4b` metric columns + top
finding → **5**/`6a` — or add to R10.4 the rule R10.5(b) already uses for `metrics.k8s.io`:
*columns whose source phase has not run render `—` with a source-pending marker, and the
requirement is re-validated (not first validated) when the source lands.*

## Findings: MAJOR

### M1 — R16.7's own text still says "Phase 5 onward", and Phase 5 keeps an acceptance criterion for an artifact A4 now owns at 1b

R16.7 (line 521): *"…a **Playwright** end-to-end suite over the **R10.3 page set**, and
**visual-regression** snapshots for the R10.28 empty-state catalogue. **Phase 5 onward.**"*
§7.3 now says `16.7 → **1b** (harness created with the SPA)`. Both cannot be true. At 1b the R10.3
page set does not exist (R10.3 → 5) and the R10.28 catalogue doesn't either (→ 6b), so the
requirement's stated scope is unbuildable at the phase that now owns it.

Downstream, Phase 5's acceptance still ends *"Vitest + Playwright suites green"* — A2's phase now
carries an acceptance criterion that tests an artifact created and owned by A4 in a phase A2 does
not control. **Fix:** R16.7 → *"Phase 1b onward (harness created with the SPA)"*; scope the
Playwright suite to *"the page set that exists at this phase"*; reword Phase 5's clause to *"the
1b harness still passes and covers the pages added at this phase"*.

### M2 — The shared 1a/1b validation entry serializes A1's Phase 2 behind A4's UI work

§7's preamble: *"1a and 1b are one phase with two owners, so they share a single validation entry
covering both halves."* Combined with R14.2's rule (*"No phase starts before the previous phase's
validation entry is written"*), this means **A1's Phase 2 now gates on A4 finishing the SPA** — it
previously gated only on A1's own Phase 1. The split's stated purpose is parallelism; the shared
entry reintroduces the dependency it was meant to remove, on the critical path.

Answer to the coordinator's second question: it is coherent with R14.2's *letter* (one phase → one
entry), but R14.2 was written when every phase had exactly one owner. **Fix:** extend R14.2 —
*a phase with more than one owner writes one entry per owner; each later phase gates on the entries
belonging to its own owner* — so Phase 2 gates on 1a's entry only, and Phases 5/6a gate on 1b's.
This is also what `IMPLEMENTATION.md` §3 needs to look like: two rows, two entries, not one row
with one entry half-written.

### M3 — 1b's headline acceptance requires editing a file in A1's package, and Phase 1a's deliverable list doesn't mention it

1b's first acceptance clause is *"The SPA is served by the Go binary at `/` (no separate web
server)"*. That is R10.1's `go:embed`, and the file that implements it lives in the Go tree A1
owns: `internal/api/server.go` currently routes exactly four paths —

```go
mux.HandleFunc("GET /healthz", s.handleHealthz)
mux.HandleFunc("GET /readyz", s.handleReadyz)
mux.HandleFunc("GET /api/v1/version", s.handleVersion)
mux.HandleFunc("GET /metrics", s.handleMetrics)
```

— with no `GET /` and no embed anywhere in the repo (`grep -rn go:embed --include='*.go' .` → no
matches). `web/vite.config.ts` already references `web/embed.go`; that file does not exist. And
Phase 1a's deliverable list — *"Discovery + kube client (per-port transport table) +
`/api/v1/clusters` + `/healthz` + `/readyz`"* — never mentions serving the SPA, so the Go-side
half of R10.1 is in nobody's Phase 1a scope while its acceptance is in A4's.

**Fix:** name the embed site explicitly — add `web/embed.go` + the `GET /` and `GET /c/**` routes
to Phase 1a's deliverables (A1 owns the Go file) or move R10.1's Go-side half to 1a and keep the
React app in 1b. Either way, one sentence saying who writes `embed.go`.

### M4 — R10.16 at 1b is real but stubbable: 2 of its 7 state dimensions exist at that phase

Answer to the coordinator's third question. R10.16 requires *"page, cluster, selected row, tab,
sort, filters and time range"* to all serialize. At 1b only **page** and **sort** can exist —
time range is R10.15 (→ 5), tabs are R10.18–R10.23 (→ 6b), filters are part of R10.15/R10.17 (→ 5).
So it is a real requirement, not a stub — serializing routes for pages that don't exist yet is
exactly what `web/src/state/urlState.ts` does, and its documented URL grammar (`/c/ns/name?tab=…`,
`?row=…`, `?range=7d`) is the right shape to build first. The risk is purely in the acceptance
vocabulary: R10.16 can be marked `validated` at 1b with five of seven dimensions unimplemented.

**Fix:** annotate it the way R9.7 is annotated — *"`R10.16` (page, sort) → **1b** · (complete) →
**5** · re-validated at **6a**, **6b** as tabs and filters land"* — and have 1b's acceptance cite
the subset explicitly, as it already does for R10.4.

### M5 — §6's Phase column is not generated from the index, and the two preambles name different sources

A3-M8's fix in v0.2.0 was to *generate* the column; the claim was added without regenerating the

## Findings: MINOR

### N1 — R10.2's verifiability clause is satisfied; the *evidence* is unfalsifiable

Answer to the coordinator's fourth question: **yes, as written.** R10.2 requires that "the decision
— chosen *or* fallen back — is recorded in `IMPLEMENTATION.md` §4 as a dated entry", and D12 is
exactly that: dated 2026-11-20, names the fallback verbatim (`@visx` over `d3-scale`, no
Chart.js/Recharts wrapper), and states it is the fallback rather than a skill-named choice. The
clause is met.

What's missing is proof of the antecedent. *"The skill was read in full (procedure + all seven
references)"* and *"it deliberately names **no** chart library"* are assertions with no citation —
the skill is not vendored in the repo (no `dataviz` file exists under `~/.claude/` or the project's
`.claude/`), so nothing in the repo can confirm or refute the claim. **Fix:** require the entry to
cite the skill path + a content hash (or the list of files read) and quote the line that would have
named a library. The same entry should link the `web/src/styles/tokens.css` it produced — that file
now exists and is the concrete artifact of the palette validation D12 describes.

### N2 — R10.2's structure is decorative for library selection

D12 establishes that the skill is a *method and design-system* skill that names no library **by
design** — which means the "if the skill yields no named library" branch fires always, and R10.2's
headline ("Chart library … **chosen by the `dataviz` skill**") can never be literally true. Split
the two claims in the requirement text: design system from the skill; library from the named
default, with the skill consulted first.

### N3 — The palette's contrast relief depends on a requirement five phases away

D12 records light-mode contrast **WARN** → "relief obligated, satisfied by **R10.23's** non-colour
encoding plus the skill's mandatory table-view twin". R10.23 is scheduled at **6b**. So 1b ships
the charts whose documented contrast relief doesn't exist for five more phases. Either pull
R10.23's non-colour encoding forward with 1b (it's small — `web/src/components/StatusGlyph.tsx`
already exists), or have D12 name the interim relief explicitly.

### N4 — The §7.2 note's "de-risks R8.11" argument doesn't hold

The note justifies the split partly with *"(ii) it de-risks **R8.11** and **R10.14** — the batched
series endpoint and the <1.5 s load budget are designed *for* the UI"*. R10.14 (Fleet's own load
budget) — yes. R8.11 (batched series endpoint) serves the **Queries** page at 6b, which 1b doesn't
render; having the Fleet page in the room de-risks it only weakly. Drop R8.11 from the sentence, or
scope it to R8.10/R10.14.

### N5 — `IMPLEMENTATION.md`'s Phase 0 row and R11.1 note carry the split's stale text

The R11.1 row says *"the collector (P2) and **UI (P5)** fill the same binary"* — post-split the UI
is P1b. And the Phase 0 Req IDs list inherits B2's `11.1–11.7, 11.9–11.16` gap, so §3.3's R14.8
table has no R11.8 row to grow into Phase 2.

### N6 — R10.1's "works fully offline inside the cluster" has no test, and CI never builds the bundle

`web/index.html` contains zero external URLs (verified) — good. But nothing asserts it stays that
way, and CI has no job that runs `npm ci && npm run build` (jobs are `build, lint, test, helm,
image`), so `web/dist` never exists in CI and the R11.4 SPA-bundle step always prints its fallback
line — which itself says *"n/a in Phase 0 (**lands in Phase 5**)"*, now wrong per the split.
**Fix:** add a `web` CI job (build + `vitest run` + Playwright screenshot job), and one grep
assertion that the built `index.html` references no off-origin URL. `vite.config.ts` already pins
`entryFileNames: "assets/index.js"` un-hashed specifically so CI's fixed path check works — the CI
message just needs to stop saying Phase 5.

## Findings that require a new requirement ID

**R24 — API response fixtures (`testdata/api/*.json`).** A checked-in response fixture per
endpoint, created by the phase that first serves it (1a: `clusters.json` with the 4 reference
clusters), consumed by the SPA's tests and R16.7's visual suite. Today the contract lives in
`web/src/api/fixtures.ts` (TypeScript, A4's tree) while R16.3's Go-side fixture corpus is at
Phase 2 — so the only machine-readable copy of the Phase 1a contract is in the *consumer's*
language, in an untracked directory. R16.3 should cover API JSON, not just metric expositions and
`pg-status` outputs.

**R25 — Split-phase validation entries.** Extend R14.2: *a phase with more than one owner writes
one validation entry per owner; each later phase gates on the entries belonging to its own owner.*
Without it, every future split phase inherits M2's cross-agent serialization.
