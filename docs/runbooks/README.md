# Runbooks

Two alert sets, two sets of runbooks, and the file names say which is which.

The reason there are two is R9.11. Its wording is explicit that our `PrometheusRule`
exists because CNPG's own `cnpg-default-alerts` lacks a `critical` tier (all 7 of its
rules are `warning`) and lacks `runbook_url` entirely — "the runbook linkage gap from the
CNPG alert set". So one set documents the rules **pgsi ships**, and the other documents
the **Postgres/CNPG alerts an operator already has** and needs to read alongside them.
They are not two spellings of one set, and no rule appears in both.

## Naming scheme

`docs/runbooks/<kebab-case-slug>.md`, one file per alert. The slug is generated by the
chart's `runbook_url` annotation and consumed by Alertmanager, so the chart's spelling is
the load-bearing one and every file here follows it. Earlier files used `PascalCase.md`;
those were renamed, and the two sets are now distinguishable by prefix alone — `pgsi-*`
is ours, `pg-*` is the Postgres/CNPG surface.

runbooks change with them. The other twelve read metrics the spec names exactly (R9.8's
self-observability set, R9.12's `pgsi_up`, R11.3's `pgsi_build_info`).

## Known duplication

Two files in set 2 describe pgsi's own surface under Postgres-style names and therefore
duplicate two files in set 1:

- `pgsi-unreachable.md` (`PGSIUnreachable`, "our `/metrics` is not scraped") duplicates
  `pgsi-not-scraped.md` (`PGSINotScraped`, `absent(pgsi_build_info)`) — same fault, two
  alert names, only one of which the chart emits.
- `pg-collector-scrape-failing.md` (`PGCollectorScrapeFailing`) duplicates
  `pgsi-collector-errors.md` (`PGSICollectorErrors`).

They are kept because each documents a rule its own vocabulary asks for, and deleting one
half of a pair is a rule-set decision, not a docs decision. Flagged rather than silently
merged.

## Requirement IDs

R14.4 is the requirement that `docs/` holds per-feature runbooks. R9.11 is the requirement
that the chart's rules carry `runbook_url` at all — the linkage this directory satisfies.
R10.26 is the UI surface that renders those links ("firing and pending alerts for a
cluster … each with its `runbook_url` linked", Phase 6a), which is why the URLs are
absolute GitHub URLs rather than relative paths: an Alertmanager inbox and the SPA both
have to resolve them.
