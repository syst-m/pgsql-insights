# Changelog

All notable changes to `pgsi`, per [R14.6](requirements.md). R14.6 asks for the
file to be maintained from Phase 1 onward rather than retro-fitted at release, and
this file is not that: it is created here, at Phase 9, so every entry below is
transcribed from `IMPLEMENTATION.md`'s §3 validation entries rather than written
when each phase closed. Phases 2 and 3 have no §3 validation entry yet — both are
mid-phase — so their two sections are derived from the commit chain instead, and
get rewritten from the entries when each phase closes. From this commit the rule
holds literally — add your entry to `[Unreleased]` in the same commit as the
change.

The project is pre-1.0 and the spec is at v0.3.0 (see
[`requirements.md`](requirements.md)); the chart's `appVersion` is `0.1.0-dev`.
Phases are the spec's own numbering, and a phase being *specified*, *built* and
*validated* are three different states that [`IMPLEMENTATION.md`](IMPLEMENTATION.md)
tracks per requirement — this file records what shipped, not what is planned.

### Changes to frozen requirements

`requirements.md` is frozen after v0.3.0 and moves only by a numbered ruling in
`IMPLEMENTATION.md` §4, so those rulings are the changelog for the contract. They
are filed here as *changes* deliberately: a CHANGELOG that files a scope change
under *fixes* is rewriting history the same way a release that ships a feature and
calls it a bugfix does. v0.3.0 itself split Phase 1 into 1a (backend) + 1b (web UI)
and incorporated the architecture review (4 blocking, 8 major, 6 minor).

- **Phase 1 split into 1a (backend, A1) + 1b (web UI, A4), and the SPA moved from
  Phase 5 to 1b** (D13). The spec's own v0.3.0 wording; §4 records it as a
  sequencing error rather than a spec gap — R10 was fully written, but the phases
  were ordered by data dependency instead of by what the product is judged on.
- **R8.1's OpenAPI half split into R8.1, R8.1b and R8.1c** (D13, from A3's review
  of `f9aae41`). One sentence covering three separately-statusable clauses meant
  "implemented" could be true while the document was hand-authored beside the code
  and unvalidated in CI; R8.1b is "generated from the code", R8.1c is "validated
  in CI". The two new ids exist so the parent can be false in part.
- **`lock_time` added to R9.4's aggregate members** (the `f9aae41` review,
  incorporated by D16) — a post-0.3.0 change to a frozen requirement made by
  ruling rather than by drift. The one that matters, because it added a field to a
  requirement whose member list was closed: an entry filed under *fixes* would
  imply the metric was always meant to be there and had simply gone unshipped.
- **R8.10's `meta.total` ruled to be the pre-cut count, not a served count, and
  `/healthz` + `/readyz` ruled never auth-gated under any value of `--auth`**
  (D18, closing A3's two open Phase 1a findings). The first is the reading R10.22's
  banner rule depends on — the served count comes from `data.length`, and
  `meta.total` is the number the page was cut from, which is why the frontend
  cannot derive one from the other.
- **R13.1's "SQL round-trips" ruled to count queries and not transaction control
  statements, and R9.7's export set ruled to be the union of R5.2's enumerated
  families with R2.4's numeric columns for the target major** (D20, A3's review of
  `fea3571`). R5.2's list is a floor, not a ceiling; the statement-counting reading
  of R13.1 puts a thirteen-collector round at 117 round-trips against a "< 40"
  budget, which is unsatisfiable by construction rather than merely over budget.
- **Chart library recorded as `@visx` over `d3-scale`** (D12) — recorded, not
  changed. R10.2 requires the choice be recorded in §4 and names no library
  itself, so the requirement moved not at all; it is here because the record is
  what R10.2 asks for.

### Fixes to the spec text

Not every ruling is a scope change, and filing these under *changes* would
overstate them as loudly as filing `lock_time` under *fixes* would understate it.

- **`requirements.md:203`'s `pg_extensions` corrected to `pg_extension`** (D19).
  The cell put an S3 query name inside an S2 relation list: the CNPG exporter's
  query #14 is *named* `pg_extensions` and reads `pg_available_extensions`, while
  the S2 relation R3.1 names is `pg_extension`. Invisible for the two entries
  where the exporter's query name and the Postgres relation name are the same
  string, wrong at the third. Fixed in place rather than on a new line because
  `IMPLEMENTATION.md:734` cites that line and the parity checker resolves the
  citation.
- **`ci.yml`'s coverage gate attributed to R11.11, not R14.5** (`0d707da`), and the
  two stale test-count families corrected across seven lines (`9ca2ed9`).
- **Citation repairs** (`docs/agents.md` §5.1's citation half, `f12857c`):
  `d72e23c` replaced the parity matrix's neighbour numbers with the whole matrix,
  and `3558f53`, `041392b` and `b57fea6` re-pointed the §3.9 chart-README cites
  that `ed58452` had shifted — the class of rot that made `docs/agents.md` §5.1
  rule 4 a rule.

## [0.1.0] — the prior release this spec rewrites

The 0.1.0 line is what v0.2.0 and v0.3.0 of the spec were written against: it had
`pgsi_scrape_target_up` (CNPG's up) and no metric for pgsi itself, no `runbook_url`
linkage, a letter-suffixed requirement ID scheme (`R9.9b`), and 18 requirement IDs
that were defined and scheduled in no phase. R9.12 (`pgsi_up`), R9.11's
`runbook_url` annotations, the ID-scheme cleanup (A3-N2) and R14.8's
requirement→file→status table are each a response to one of those gaps.
